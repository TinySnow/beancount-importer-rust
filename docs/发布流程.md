# 发布流程

本文给出该项目当前推荐的对外发布方式与操作步骤。

## 1. 推荐方案（当前最佳）

使用 **GitHub Releases + tag 触发的 GitHub Actions 自动构建**。

原因：
- 用户无需安装 Rust 工具链，下载即用。
- 统一产出多平台二进制，降低用户环境差异问题。
- 产物可附带校验和，便于验证完整性。
- 发布动作标准化，减少手工打包失误。

当前 workflow 文件：
- `.github/workflows/release.yml`

## 2. 发布产物约定

每个平台产物均包含：
- 可执行文件 `beancount-importer-rust`（Windows 为 `.exe`）
- `config/`
- `mapping/`
- `README.md`
- `LICENSE`

发布页额外提供：
- `SHA256SUMS`

说明：
- 该项目现有不少 provider 配置显式依赖 `mapping_file`，因此发布包必须包含 `mapping/`。
- 若仅分发二进制而不带 `config/` 与 `mapping/`，用户很容易因路径缺失导致运行失败。

## 3. 版本与分支建议

推荐约定：
- 开发分支：`main`
- 发布版本号：`vMAJOR.MINOR.PATCH`（示例：`v0.2.0`）
- tag 必须对应可回溯 commit（避免本地临时改动未入库）

## 4. 发布前检查

在仓库根目录执行：

```bash
cargo fmt --check
cargo test --quiet
```

至少再跑两个端到端样本：
- 1 个现金流 provider（如 `alipay`）
- 1 个证券 provider（如 `yinhe`）

并确认：
- README 与 docs 命令、路径、字段名与代码一致。
- `CHANGELOG.md` 已更新到本次版本。
- `Cargo.toml` 版本号已更新到目标版本。

## 5. 正式发布步骤

1. 提交本次版本相关变更（代码、配置、文档、changelog）。
2. 打 tag：

```bash
git tag v0.2.0
git push origin v0.2.0
```

3. 等待 GitHub Actions `Release` workflow 完成。
4. 到 GitHub Releases 页面检查：
- 4 个平台包是否齐全（Linux / Windows / macOS x64 / macOS arm64）。
- `SHA256SUMS` 是否存在。
- 自动生成发布说明是否准确。

## 6. 发布后验收（维护者视角）

建议从 Release 下载任意一个平台包，做一次冒烟测试：

```bash
./beancount-importer-rust --help
```

并至少验证一条导入命令可运行（可用测试样本）。

## 7. 回滚与热修建议

若发现严重问题：
1. 立刻创建修复 commit。
2. 重新发补丁版本（如 `v0.2.1`），不要覆盖已有 tag。
3. 在新版本 release notes 首段标注修复内容与影响范围。

不建议直接修改已发布 tag 对应内容，这会破坏可追溯性。
