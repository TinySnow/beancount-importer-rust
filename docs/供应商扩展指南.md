# 供应商扩展指南

按步骤接入新供应商，产出可合并的 PR。

适用范围：
- 银行（`banks`）
- 第三方支付（`third_party`）
- 证券（`securities`）

## 0. 最终交付标准（Definition of Done）

一个“可合并”的供应商接入 PR，至少满足以下条件：

1. 新 provider 可通过 CLI 正常运行（`--provider <name>` 可识别）。
2. 有对应的 provider 配置文件：`config/<category>/<name>.yml`。
3. 有对应的映射文件：`mapping/<category>/<name>.yml`。
4. 使用新配置格式（`default:` / `securities_accounts:`），不使用旧平铺键。
5. 使用真实样本在普通模式和 strict 模式都跑过。
6. `cargo test --quiet` 通过。
7. 文档已更新（至少更新本指南提到的相关条目）。

## 1. 接入前先做的决策

### 1.1 先判断是否需要写 Rust 代码

如果只是“同一 provider 的新账单模板/新列名变体”，通常只改 YAML：
- 改 `config/.../*.yml`
- 改 `mapping/.../*.yml`

如果是“新 provider 名称”，必须新增 Rust provider 并注册：
- 新建 `src/providers/<category>/<name>.rs`
- 在 `src/providers/<category>/mod.rs` 暴露模块并添加到 `all()` 函数

### 1.2 选择分类目录

分类固定三种：
- `third_party`
- `banks`
- `securities`

配置与映射路径会按分类 fallback：
- 配置：`config/{third_party|banks|securities}/<provider>.yml`
- 映射：`mapping/{third_party|banks|securities}/<provider>.yml`

## 2. 你需要改哪些文件（按场景）

### 2.1 新增一个“普通现金流”provider（银行/三方）

必改文件：
1. `src/providers/<category>/<name>.rs`
2. `src/providers/<category>/mod.rs`（加 `pub mod <name>;` 并在 `all()` 中添加实例）
3. `config/<category>/<name>.yml`
4. `mapping/<category>/<name>.yml`

建议补充：
1. `docs/配置详解.md`（如果引入了新的规则写法或字段约定）
2. `README.md`（支持列表/示例命令）
3. `examples/...`（如果希望提供可复用模板）

### 2.2 新增一个“证券”provider

必改文件与现金流相同，但配置建议额外包含：
1. `securities_accounts.cash_account`（强烈建议显式配置）
2. `output.booking_method: "FIFO"`（跨账期 lot 二义性更少）

### 2.3 只做“同 provider 新模板适配”

通常仅改：
1. `mapping/<category>/<name>.yml`
2. `config/<category>/<name>.yml`（如果导出格式变化导致 delimiter/encoding/header 变化）

### 2.4 改动矩阵（文件 -> 你要改什么）

| 文件 | 你要改什么 | 不改会怎样 |
|---|---|---|
| `src/providers/<category>/<name>.rs` | 定义 provider 常量参数、`name()`、`description()`、`transform()` | CLI 可识别但无法执行对应转换逻辑 |
| `src/providers/<category>/mod.rs` | `pub mod <name>;` + 在 `all()` 中添加实例 | 编译时找不到模块 |
| `config/<category>/<name>.yml` | 定义默认账户、读取参数、规则、mapping 路径 | 账户回退不可控、读取参数不稳定 |
| `mapping/<category>/<name>.yml` | 定义列到标准字段映射 | 出现 `Missing date/amount/...` 或方向误判 |
| `docs/配置详解.md`（按需） | 新字段/新规则行为文档化 | 评审无法判断行为边界 |

### 2.5 建议执行顺序（按这个顺序最快）

1. 确定 `provider id`（小写、稳定、不要改名）。
2. 选一个最接近的现有 provider 文件复制为新文件。
3. 先接通 Rust 最小骨架（`name/description/transform`）。
4. 修改 `mod.rs` 暴露与 `provider_registry` 注册。
5. 写 `mapping` 最小可用版：先保证 `date`、`amount` 可读。
6. 写 `config` 最小可用版：先保证 `default.*`、读取参数正确。
7. 用真实样本跑普通模式，确认能产出 `.beancount`。
8. 用同一份样本跑 strict 模式，修掉解析/映射错误。
9. 再补 `rules` 和 `extra_fields`，优化分类与元数据。
10. 最后跑 `cargo test --quiet`，整理 PR 描述并提交。

## 3. 字段映射（mapping）最佳实践

### 3.1 先明确两层字段

映射有两层：
1. 标准字段：写到 `RawRecord` 的结构化字段（如 `date/amount/payee/...`）。
2. 扩展字段：写到 `extra_fields`，供规则和 metadata 使用。

标准字段定义见 `src/model/mapping/field_mapping.rs`，当前支持：
- 现金流通用：`date` `amount` `currency` `payee` `narration` `transaction_type` `status` `reference`
- 证券通用：`symbol` `security_name` `quantity` `unit_price` `fee` `tax`

### 3.2 简写与详写

简写：
```yaml
date: "交易时间"
amount: "金额"
```

详写（推荐用于脏数据列）：
```yaml
amount:
  column: "金额(元)"
  transform: abs
reference:
  column: "摘要"
  regex_extract: "订单号[:：]?\\s*(\\d+)"
currency:
  column: "币种"
  default: "CNY"
```

详写字段能力：
- `default`：空值回填
- `transform`：常用 `abs` / `negate`
- `regex_extract`：先取第 1 捕获组，若无则取完整匹配

### 3.3 `extra_fields` 推荐写法

推荐：`metadata_key -> source_column`

```yaml
extra_fields:
  orderId: "交易单号"
  payTime: "交易时间"
  peer: "交易对方"
```

说明：
- 运行时仍兼容旧反向写法（`source_column -> metadata_key`），但新 PR 一律使用推荐写法。

### 3.4 日期格式必须显式列出你的真实样本格式

```yaml
date_formats:
  - "%Y-%m-%d %H:%M:%S"
  - "%Y/%m/%d"
```

建议：
- 如果账单导出有多个格式，全部列出。
- 如果是 Excel 序列日期，当前读取层支持自动解析，但仍建议保留常见字符串格式。

### 3.5 按业务类型的“内部必填字段”

这里的“必填”是指：缺失时会在转换阶段报错，或者导致不可靠推断。

### 3.5.1 现金流（banks / third_party）

硬必填：
1. `date`
2. `amount`

强烈建议提供：
1. `transaction_type`（方向判断更稳定）
2. `payee`
3. `narration`
4. `currency`
5. `reference`

说明：
- 没有 `transaction_type` 时，系统会回退到金额符号推断收支方向。
- 这在退款、冲正、手续费混合列里容易误判，因此建议始终映射 `transaction_type` 或 `extra.type`。

### 3.5.2 证券（securities）

公共硬必填：
1. `date`

证券交易路径（买卖/逆回购）硬必填：
1. `symbol`
2. `quantity`
3. `amount` 或 `unit_price`（二者至少一个）

银证转账路径硬必填：
1. `amount`
2. `transaction_type`（建议包含“银行转证券/证券转银行/银证转入/银证转出”等）

强烈建议提供：
1. `currency`
2. `reference`
3. `fee` `tax`（用于 metadata 与利润信息）

### 3.6 映射文件审查清单（提交前自查）

1. 每个标准字段都能在样本表头找到对应列。
2. 金额列是否需要 `abs/negate`。
3. 日期格式是否覆盖样本实际值。
4. `extra_fields` 是否只放真正用于规则/审计的字段。
5. 是否存在明显错拼列名（strict 模式会暴露）。

### 3.7 无表头文件怎么映射（`has_header_row: false`）

当源文件没有表头时，读取层会自动生成位置列名：`col_0` 到 `col_255`。  
你应在 mapping 里使用这些列名：

```yaml
date: "col_0"
amount:
  column: "col_3"
  transform: abs
payee: "col_5"
transaction_type: "col_6"
```

配套 config 示例：

```yaml
skip_header_lines: 0
has_header_row: false
```

### 3.8 金额与方向的三种常见映射模式

模式 A：单金额列 + 明确方向列（最稳）

```yaml
amount:
  column: "金额"
  transform: abs
transaction_type: "收支类型"
```

模式 B：收入/支出分列（常见银行格式）

- 可不显式映射 `amount`，由读取层按常见键自动推断金额与方向。  
- 推断键包含：  
`支出/出账金额/出账/借方金额/借方发生额/debit/debit_amount/withdrawal`  
`收入/入账金额/入账/贷方金额/贷方发生额/credit/credit_amount/deposit`  

实践建议：
- 即使依赖分列推断，也尽量把原始分列放进 `extra_fields` 便于排查：

```yaml
extra_fields:
  incomeAmount: "记账金额(收入)"
  expenseAmount: "记账金额(支出)"
```

模式 C：金额永远为正，方向靠文本描述

- 必须映射 `transaction_type` 或 `extra.type`，否则只靠金额符号会误判。  
- 推荐让 `transaction_type` 的原始值包含“收入/支出/转入/转出”语义词。

### 3.9 规则里可以匹配哪些字段（`field:` 可用键）

规则引擎读取的是 `RawRecord::get`。  
常用可匹配键：

1. 标准键：`payee` `narration` `transaction_type` `status` `reference` `symbol` `security_name` `currency`
2. 方向兼容键：`type`（优先读 `extra.type`，否则回退 `transaction_type`）
3. 扩展键：你在 `extra_fields` 里定义的任意 key（如 `orderId` / `peer` / `payTime`）
4. 保留扩展键：`peer`、`peerAccount`

实践建议：
- 想让规则长期可维护，优先匹配“规范化后的 key”，不要直接匹配原始中文列名。

### 3.10 映射调试流程（推荐固定动作）

1. 先跑普通模式（`--log-level info`）确认能读出 headers。  
2. 再跑 `--log-level debug` 看更细日志（比如无表头时是否走了 `col_x`）。  
3. 再跑 strict 模式定位“第一条失败记录”的行号与原因。  
4. 只改一处映射后重跑，不要一次改很多列。  

建议命令：

```bash
cargo run -- --provider <name> --source <sample> --config config/<category>/<name>.yml --output tmp/output/<name>.beancount --log-level debug
cargo run -- --provider <name> --source <sample> --config config/<category>/<name>.yml --strict --log-level debug
```

### 3.11 两套可直接起步的 mapping 模板

现金流模板：

```yaml

  column: "金额"
  transform: abs
transaction_type: "收/支"
payee: "交易对方"
narration: "摘要"
reference: "交易单号"
currency: "币种"
date_formats:
  - "%Y-%m-%d %H:%M:%S"
  - "%Y-%m-%d"
extra_fields:
  orderId: "交易单号"
  payTime: "交易时间"
```

证券模板：

```yaml

transaction_type: "业务类型"
symbol: "证券代码"
security_name: "证券名称"
quantity: "成交数量"
unit_price: "成交价格"

fee: "手续费"

  - "%Y%m%d"
```

## 4. provider 配置最佳实践（config）

### 4.1 只使用新格式

必须使用：
- `default.asset_account`
- `default.expense_account`
- `default.income_account`
- `default.currency`

证券可选增强：
- `securities_accounts.cash_account`
- `securities_accounts.fee_account`
- `securities_accounts.pnl_account`
- `securities_accounts.rounding_account`
- `securities_accounts.repo_interest_account`

注意：
- 旧平铺键（`default_asset_account` 等）已移除，使用会在加载时报错。

### 4.2 `mapping_file` 路径策略

推荐显式写：
```yaml
mapping_file: "mapping/<category>/<provider>.yml"
```

相对路径解析顺序：
1. 相对 provider 配置文件目录
2. 相对当前工作目录

### 4.3 读取参数（经常决定能否读通）

最常改字段：
1. `tabular_options.delimiter`
2. `tabular_options.encoding`
3. `tabular_options.flexible`
4. `skip_header_lines`
5. `has_header_row`

实践建议：
- CSV 通常：`delimiter: ","`, `encoding: "auto"`
- 券商导出“伪 xls 文本”常见：`\\t + GBK`
- 首次调试先 `flexible: true`，稳定后再收紧

### 4.4 两套可直接起步的 config 模板

现金流 provider 最小模板：

```yaml
name: "示例平台"
mapping_file: "mapping/<category>/<provider>.yml"

default:
  asset_account: "Assets:Wallet:<Provider>:Balance"
  expense_account: "Expenses:Unknown"
  income_account: "Income:Unknown"
  currency: "CNY"

tabular_options:
  delimiter: ","
  flexible: true
  encoding: "auto"

skip_header_lines: 0
has_header_row: true

output:
  date_format: "%Y-%m-%d"
  decimal_places: 2

rules: []
```

证券 provider 最小模板：

```yaml
name: "示例券商"
mapping_file: "mapping/securities/<provider>.yml"

default:
  asset_account: "Assets:Broker:<Provider>:Securities"
  expense_account: "Expenses:Investing:Fees"
  income_account: "Income:Investing:Capital-Gains"
  currency: "CNY"

securities_accounts:
  cash_account: "Assets:Broker:<Provider>:Cash"

tabular_options:
  delimiter: ","
  flexible: true
  encoding: "auto"

skip_header_lines: 0
has_header_row: true

output:
  date_format: "%Y-%m-%d"
  decimal_places: 4
  booking_method: "FIFO"

rules: []
```

### 4.5 规则策略建议（减少后续代码改动）

1. 优先把分类逻辑放 `rules`，不要急着在 Rust 里写分支。
2. 规则先写“忽略类”（如撤销/失败/非交易行），再写业务分类规则。
3. 用 `priority` 明确覆盖顺序，避免“偶然命中”。
4. 对证券规则，只有确实需要时才覆盖 `fee_account/pnl_account/rounding_account`。
5. 同一个语义尽量统一键名（如统一使用 `type` / `txType`），便于后续复用规则。

## 5. Rust 代码接入步骤（新 provider）

### 5.1 新建 provider 文件

现金流 provider 模板：
```rust
use std::path::Path;

use crate::{
    error::ImporterResult,
    interface::provider::{Provider, parse_tabular_source},
    model::{
        config::provider::ProviderConfig,
        data::raw_record::RawRecord,
        mapping::field_mapping::FieldMapping,
        rule::rule_engine::RuleEngine,
        transaction::Transaction,
    },
    providers::shared::{CashflowTransformOptions, transform_cashflow_record},
};

const XXX_OPTIONS: CashflowTransformOptions = CashflowTransformOptions {
    default_asset_fallback: "Assets:XXX",
};

pub struct XxxProvider;

impl Provider for XxxProvider {
    fn name(&self) -> &'static str { "xxx" }

    fn description(&self) -> &'static str { "XXX statement importer" }

    fn display_name(&self) -> &'static str { "某某平台" }

    fn parse(
        &self,
        path: &Path,
        mapping: &FieldMapping,
        config: &ProviderConfig,
        strict_mode: bool,
    ) -> ImporterResult<Vec<RawRecord>> {
        parse_tabular_source(path, mapping, config, strict_mode)
    }

    fn transform(
        &self,
        record: RawRecord,
        rule_engine: &RuleEngine,
        config: &ProviderConfig,
    ) -> ImporterResult<Option<Transaction>> {
        transform_cashflow_record(
            self.name(),
            self.display_name(),
            XXX_OPTIONS,
            record,
            rule_engine,
            config,
        )
    }
}
```

证券 provider 模板：

### 5.2 暴露模块

在 `src/providers/<category>/mod.rs` 增加：
```rust
pub mod xxx;
```

### 5.3 注册 provider

在 `src/runtime/provider_registry.rs` 的 `GLOBAL_REGISTRY` 初始化里增加：
```rust
registry.register(Arc::new(<category>::xxx::XxxProvider));
```

命名规范：
- `name()` 返回值必须全小写，和 CLI `--provider` 一致。

### 5.4 何时需要覆盖 `parse`

默认使用 `parse_tabular_source` 辅助函数实现 `parse()`（参考上方模板）。

仅在以下场景才需要自定义 `parse`：
1. 文件不是常规 CSV/XLS/XLSX 表格。
2. 需要非常规预处理（多表合并、跨文件 join、非标准行分隔）。

否则在 `parse()` 中调用 `parse_tabular_source(path, mapping, config, strict_mode)` 复用通用表格解析逻辑，避免重复实现。

### 5.5 何时需要写“provider 特化逻辑”

90% 的接入只需共享转换器（cashflow/securities）+ YAML。  
只有遇到以下情况才建议在 provider 文件中做特化：

1. 上游交易类型必须先归一化，否则共享逻辑无法正确分流。  
2. 某类记录要走专门分录路径（例如“利息归本但无证券代码”）。  
3. 必须在进入共享逻辑前注入平台专属字段修正。  

如果你需要特化，建议遵循模式：

1. 在 provider 内新增一个小函数做“记录归一化”。  
2. 先处理特例分支，剩余记录全部回落共享转换器。  
3. 不要复制 shared 里的完整分录逻辑，避免后续漂移。  

### 5.6 新 provider 常见遗漏（代码层）

1. `name()` 和注册表键不一致（大小写/拼写）。  
2. 只在 `src/providers/<category>/mod.rs` 暴露了模块，但没添加到 `all()` 函数中。  
3. 配置和映射落在错误目录（比如证券文件放进 `banks`）。  
4. 未实现 `display_name()`，导致 `source` 元数据退化为英文名。  
5. `default_asset_fallback` 过于泛化，产出账户不可用。  

### 5.7 关键代码定位（需要读哪里）

1. Provider trait 定义：`src/interface/provider.rs`  
2. 注册表：`src/runtime/provider_registry.rs`  
3. 配置加载与 fallback：`src/runtime/config_loader/*.rs`  
4. 标准映射字段定义：`src/model/mapping/field_mapping.rs`  
5. 表格映射实现：`src/runtime/reader/tabular/mapping/mapper/`（`mod.rs` 编排层、`record_mapper.rs` 单行映射、`field_resolver.rs` 字段解析）  
6. 现金流共享转换：`src/providers/shared/cashflow/transform.rs`  
7. 证券共享转换入口：`src/providers/shared/securities/transform.rs`  

## 6. 如果你需要“新增标准字段”而不是仅接入 provider

只有当现有标准字段不够表达你的业务语义时，才做这件事。

### 6.1 先判断是否真的要新增标准字段

先按顺序判断：

1. 能否只用 `extra_fields` 承载？  
如果这个字段只用于 metadata 或规则匹配，通常不需要加到标准模型。

2. 能否通过现有标准字段 + 规则表达？  
例如方向、对手方、类型等，很多场景可以通过规则组合实现。

3. 是否必须要“强类型参与转换逻辑”？  
例如要参与金额计算、证券分录构建，这类才适合升级为标准字段。

改动清单：
1. `src/model/data/raw_record.rs`
   - 新增结构字段
   - 在 `RawRecord::get` 暴露规则可读字段名
2. `src/model/mapping/field_mapping.rs`
   - 新增映射字段定义
   - 更新 `get_standard_mapping`
3. `src/runtime/reader/tabular/mod.rs`
   - 更新 `mapped_specs()` 返回数组（映射校验/表头识别会用）
4. `src/runtime/reader/tabular/mapping/mapper/record_mapper.rs`
    - 增加字段映射赋值逻辑（`map_text/map_decimal/...`）
   - 必要时补 fallback 推断
5. 如果要被规则 action 覆盖：
   - 更新 `rule_action.rs`、`match_result.rs`
   - 更新 shared transform 的账户/行为读取逻辑
6. 补测试：
   - mapping 层测试
   - transform 层测试
   - 配置文档更新

这类改动属于“模型扩展”，评审成本高于普通 provider 接入，请在 PR 描述里明确动机。

## 8. 常见失败与排查

1. `Unknown provider`
- 忘记在 `provider_registry.rs` 注册，或 `name()` 和 CLI 不一致。

2. `No field mapping file found`
- `mapping_file` 路径错误，或没放到 `mapping/<category>/<name>.yml`。

3. `Missing date` / `Missing amount` / `Missing security symbol`
- 映射漏字段，或列名拼写不一致。

4. strict 模式下大量行失败
- 表头定位错误（`skip_header_lines/has_header_row`）
- `delimiter/encoding` 不匹配
- `regex_extract` 写错

5. 证券转账被当成证券交易
- `symbol` 空但 `transaction_type` 未命中转账关键词，导致走交易路径。
- 解决：补 `transaction_type` 映射和规则归一化。

### 8.1 常见报错 -> 直接修复动作

| 报错/现象 | 常见根因 | 直接修复动作 |
|---|---|---|
| `Unknown provider` | 未注册或 `name()` 不一致 | 检查 `provider_registry.rs` 注册项和 `name()` |
| `No field mapping file found` | `mapping_file` 错或目录错 | 改为 `mapping/<category>/<provider>.yml` 并确认文件存在 |
| `Missing date` | `date` 列名映射不对/格式不匹配 | 修 `date` 映射并补 `date_formats` |
| `Missing amount` | 金额列未映射或无法解析 | 修 `amount` 映射、必要时加 `transform: abs` |
| `Missing security symbol` | 证券交易未映射 `symbol` | 修 `symbol` 映射或将该类型转账规则先 `ignore` |
| strict 下 `field count mismatch` | 分隔符/表头设置错 | 修 `delimiter`、`skip_header_lines`、`has_header_row` |
| strict 下 `Mapping error` | `regex_extract` 非法或列名拼错 | 修正正则/列名后重跑 strict |
