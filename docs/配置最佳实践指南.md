# 配置最佳实践指南（从最小可用到长期可维护）

本文目标只有一个：
让你在看完后，能快速判断“我必须配什么”“我可以不配什么”“我什么时候才需要高级配置”。

覆盖从最小可用到长期可维护的配置策略。（2026-04）。

---

## 1. 先记住：你只需要关心 3 类配置

1. `config/global.yml`（全局默认，可选）
2. `config/<category>/<provider>.yml`（某个供应商配置，核心）
3. `mapping/<category>/<provider>.yml`（字段映射，核心）

其中：
- `provider.yml` 决定“怎么读文件、默认记到哪些账户、规则怎么跑”。
- `mapping.yml` 决定“源文件每一列对应哪个标准字段”。

一句话：
- 不写 `global.yml` 也能跑。
- `provider.yml + mapping.yml` 才是最小可运行组合。

---

## 2. 配置加载与覆盖顺序（务必搞清）

运行时优先级：

1. `--global-config` 指定路径（不传则尝试 `config/global.yml`）
2. `--config` 指定 provider 配置路径
3. 若 `--config` 文件不存在，自动回退：
   - `config/third_party/<provider>.yml`
   - `config/banks/<provider>.yml`
   - `config/securities/<provider>.yml`
4. 若仍找不到 provider 文件，再尝试 `global.yml` 里的 `providers.<provider>`
5. `mapping_file` 若配置了：优先按该路径加载（相对路径先按 provider 文件目录解析，再按 cwd 解析）
6. `mapping_file` 未配置时，自动回退：
   - `mapping/third_party/<provider>.yml`
   - `mapping/banks/<provider>.yml`
   - `mapping/securities/<provider>.yml`

覆盖原则：
- Provider 配置覆盖 Global。
- Provider 缺省字段回退 Global。

字段校验策略（重要）：
- `global/provider/default/securities_accounts` 使用严格校验（未知字段会报错）。
- `mapping/rules/output/tabular_options` 当前不是严格拒绝未知字段，写错 key 可能被忽略。
- 实践建议：改配置后先跑一遍 `cargo run ... --log-level info`，看日志是否按预期命中。

## 3. 先做选择：你属于哪个场景

### 场景 A：第三方支付/银行（`alipay/wechat/jd/mt/icbc/ccb/dzccb`）
你大概率只需要：
- `provider.yml` 里的 `default`（账户+币种）
- `mapping_file`
- `skip_header_lines`、`has_header_row`
- `tabular_options.encoding`（如果不是 UTF-8）

你大概率不需要：
- `securities_accounts`
- `inventory_seed_files`
- `output.booking_method`

### 场景 B：证券（`futu/yinhe`）
你建议至少配：
- `default.asset_account`
- `securities_accounts.cash_account`
- `default.expense_account`
- `default.income_account`
- `default.currency`

你按需再配：
- `securities_accounts.fee_account`
- `securities_accounts.pnl_account`
- `securities_accounts.rounding_account`
- `securities_accounts.repo_interest_account`
- `inventory_seed_files`
- `output.emit_open_directives` / `output.booking_method`

## 4. 目录结构最佳实践

推荐固定结构（不要混放）：

```text
config/
  global.yml
  third_party/
    alipay.yml
    wechat.yml
  banks/
    icbc.yml
    ccb.yml
  securities/
    futu.yml
    yinhe.yml
mapping/
  third_party/
    alipay.yml
    wechat.yml
  banks/
    icbc.yml
    ccb.yml
  securities/
    futu.yml
    yinhe.yml
```

建议：
- `provider` 名称与文件名保持一致（如 `wechat` -> `wechat.yml`）。
- `mapping_file` 用分层路径（如 `mapping/third_party/wechat.yml`）。

## 5. 全量字段说明：`config/global.yml`

> Global 文件是“默认模板”，不是必须。

### 5.1 结构

```yaml
default:
  asset_account: "Assets:Unknown"
  expense_account: "Expenses:Unknown"
  income_account: "Income:Unknown"
  currency: "CNY"

global_rules: []

output:
  date_format: "%Y-%m-%d"
  decimal_places: 2

providers:
  wechat:
    # 这里的结构与 provider.yml 一致
```

### 5.2 字段级说明

#### `default`（推荐配置）
- `asset_account`: 全局默认资产账户
- `expense_account`: 全局默认费用账户
- `income_account`: 全局默认收入账户
- `currency`: 全局默认币种（建议总是写）

是否必须：
- 技术上不是必须。
- 实践上建议必须（至少 `currency` + 一套默认账户），否则兜底账户会更泛化。

#### `global_rules`
- 类型：`Rule[]`
- 作用：对所有 provider 生效，且先于 provider 规则执行
- 是否必须：否

#### `output`
- 全局输出格式默认项
- 是否必须：否

#### `providers`
- 可把某些 provider 配置内联到 global 文件
- 键名是 provider 标识（大小写不敏感匹配）
- 是否必须：否

何时建议使用 `providers`：
- 你想只维护一个大配置文件。

何时不建议：
- 团队协作、多人改配置时（冲突多）。

## 6. 全量字段说明：`config/<category>/<provider>.yml`

> 这是最核心的配置文件。

### 6.1 最小模板（银行/第三方）

```yaml
name: "微信"
mapping_file: "mapping/third_party/wechat.yml"

default:
  asset_account: "Assets:Wallet:WeChat:Balance"
  expense_account: "Expenses:Unknown"
  income_account: "Income:Unknown"
  currency: "CNY"

tabular_options:
  delimiter: ","
  quote: '"'
  flexible: true
  encoding: "auto"

skip_header_lines: 17
has_header_row: true

rules: []
```

### 6.2 最小模板（证券）

```yaml
name: "银河证券"
mapping_file: "mapping/securities/yinhe.yml"

default:
  asset_account: "Assets:Broker:Galaxy:Securities"
  expense_account: "Expenses:Investing:Fees"
  income_account: "Income:Investing:Capital-Gains"
  currency: "CNY"

securities_accounts:
  cash_account: "Assets:Broker:Galaxy:Cash"

tabular_options:
  delimiter: "\t"
  flexible: true
  encoding: "GBK"

skip_header_lines: 0
has_header_row: true

rules: []
```

### 6.3 字段详解（逐项）

#### `name`
- 类型：`string`
- 作用：配置标识名，便于多配置区分。不影响输出 `source` 标签（source 由 `display_name()` 决定）
- 是否必须：否

#### `mapping_file`
- 类型：`string`
- 作用：指定映射文件
- 是否必须：建议必须
- 不写时：按 provider 名自动从 `mapping/<category>/<provider>.yml` 回退

#### `default`
- 类型：对象
- 字段：`asset_account/expense_account/income_account/currency`
- 是否必须：
  - 实践上建议必须
  - 至少建议配 `currency` + `asset_account`

#### `securities_accounts`（证券用）
- `cash_account`
- `fee_account`
- `pnl_account`
- `rounding_account`
- `repo_interest_account`

是否必须：
- 非证券：不需要
- 证券：建议至少 `cash_account`

#### `inventory_seed_files`
- 类型：`string[]`
- 作用：跨账期 lot 预加载
- 路径：相对路径会按 provider 配置文件目录解析成绝对路径
- 是否必须：否

#### `tabular_options`
- `delimiter`：分隔符，默认 `,`
- `quote`：引号字符，默认 `"`
- `flexible`：是否容忍坏行，默认 `false`
- `encoding`：`UTF-8`/`AUTO`/`GBK`/`GB18030`/`BIG5` 等
- `comment`：注释前缀字符（可选）

是否必须：否（有默认值）

推荐：
- 不确定编码时优先 `encoding: "auto"`
- 历史导出脏数据多时 `flexible: true`（配合非 strict 使用）

#### `skip_header_lines`
- 类型：`usize`
- 作用：先跳过前 N 行再进入解析
- 是否必须：否，默认 `0`

#### `has_header_row`
- 类型：`bool`
- 作用：数据里是否含表头
- 是否必须：否，默认 `true`

实践建议：
- CSV/XLSX 导出若前面有说明文本：设置 `skip_header_lines`
- XLSX 且 `has_header_row: true` 时，会做“最像表头行”的自动识别

#### `rules`
- 类型：`Rule[]`
- 作用：账户/摘要/元数据覆盖与忽略策略
- 是否必须：否（可空）

#### `output`
- 供应商级写出配置（覆盖 global.output）
- 是否必须：否

## 7. 全量字段说明：`mapping/<category>/<provider>.yml`

> 映射是“能不能正确解析”的关键。

### 7.1 标准字段全集

可配置标准字段（都可选）：

- `date`
- `amount`
- `currency`
- `payee`
- `narration`
- `transaction_type`
- `status`
- `reference`
- `symbol`
- `security_name`
- `quantity`
- `unit_price`
- `fee`
- `tax`

附加字段：
- `extra_fields`（`meta_key -> source_column`）
- `date_formats`（日期格式数组）

### 7.2 你到底必须配哪些映射

#### 现金流（银行/第三方）建议最小必配
- `date`
- `amount`

建议再配：
- `transaction_type`
- `payee`
- `narration`
- `reference`

说明：
- `amount` 在一些“收入/支出分列”账单中可被兜底推断，但不应依赖推断长期使用。

#### 证券建议最小必配
- `date`
- `symbol`
- `quantity`
- `amount` 或 `unit_price`（二选一至少一个）

强烈建议再配：
- `transaction_type`
- `security_name`
- `fee`
- `tax`

因为：
- `symbol`/`quantity` 缺失会直接导致证券交易构建失败。
- `amount` 和 `unit_price` 若都缺失，也会失败。

### 7.3 `FieldSpec` 两种写法

#### 简写

```yaml
payee: "交易对方"
```

#### 详写

```yaml
amount:
  column: "金额(元)"
  default: "0"
  transform: abs
  regex_extract: "([0-9.]+)"
```

可用 `transform`：
- `abs`
- `negate`

### 7.4 `extra_fields` 最佳实践

推荐写法：

```yaml
extra_fields:
  orderId: "交易单号"
  payTime: "交易时间"
  peer: "交易对方"
  type: "收/支"
```

说明：
- 推荐 `meta_key -> 源列名`。
- 读取层仍兼容旧反向写法，但不建议继续使用。

### 7.5 `date_formats` 建议

如果源日期格式不稳定，写多个：

```yaml
date_formats:
  - "%Y-%m-%d"
  - "%Y/%m/%d"
  - "%Y-%m-%d %H:%M:%S"
  - "%Y/%m/%d %H:%M:%S"
```

## 8. 全量字段说明：规则 `rules`

### 8.1 单条规则结构

```yaml
- name: "餐饮支出"
  match_mode: and
  conditions:
    - field: "type"
      equals: "支出"
    - field: "payee"
      regex: "(咖啡|奶茶|餐饮)"
  action:
    debit_account: "Expenses:Food"
    credit_account: "Assets:Wallet:WeChat:Balance"
    metadata:
      scene: "daily"
    tags: ["food"]
    links: ["rule/food"]
    flag: "*"
  priority: 10
  terminal: false
```

### 8.2 条件操作符全集

- `equals`
- `contains`
- `regex`
- `starts_with`
- `ends_with`
- `greater_than`
- `less_than`
- `between`（`min/max`）
- `in`
- `not_empty`
- `is_empty`

`not_empty` / `is_empty` 示例：

```yaml
- field: "peerAccount"
  not_empty:
- field: "status"
  is_empty:
```

### 8.3 action 字段全集

- `debit_account`
- `credit_account`
- `fee_account`
- `pnl_account`
- `rounding_account`
- `payee`
- `narration`
- `tags`
- `links`
- `flag`
- `metadata`
- `ignore`

### 8.4 规则执行与覆盖（重要）

顺序：
1. `global_rules`
2. provider `rules`

组内排序：
1. `priority` 升序
2. `specificity`（条件数量）升序
3. 文件出现顺序

合并语义：
- 标量字段：后命中覆盖前命中
- `tags/links`：追加
- `metadata`：同 key 后命中覆盖前值
- `ignore`: 一旦 true 保持 true
- `terminal: true`：命中即停止后续规则

### 8.5 规则分层策略（第三方支付平台强推）

第三方支付平台（支付宝、微信、美团、京东）的账单有一个天然正交结构：
**付款方式** 决定 `credit_account`（钱从哪出），**消费类别** 决定
`debit_account`（钱花在哪）。两者独立，不应该在每个类别规则里重复写
付款方式。

推荐把规则拆为两层，利用标量字段的独立合并语义：

**Layer 1 — 付款方式 → credit_account（priority 100）**

```yaml
- name: "付款方式-零钱"
  conditions:
    - field: type
      in: ["支出", "不计收支"]
    - field: method
      contains: 零钱
  action:
    credit_account: Assets:Wallet:WeChat:Balance
  priority: 100

- name: "付款方式-工行卡"
  conditions:
    - field: type
      in: ["支出", "不计收支"]
    - field: method
      contains: 工商银行储蓄卡(8739)
  action:
    credit_account: Assets:Bank:ICBC:6212262318003858739
  priority: 100
```

**Layer 2 — 消费类别 → debit_account（priority 10-30）**

每条分类规则只设 `debit_account`，不写 `credit_account`，不区分付款方式：

```yaml
- name: "消费-餐饮美食"
  match_mode: or
  conditions:
    - field: peer
      regex: 小吃|火锅|餐饮
    - field: item
      regex: 小吃|火锅|餐饮
  action:
    debit_account: Expenses:Food
  priority: 17
```

效果：原来每个类别 × 每个付款方式的 N×M 条规则，变成
N（付款方式）+ M（类别）条。3 种付款方式 × 12 个类别 = **36 条 → 15 条**。

需要同时覆盖借贷双方的特殊场景（收入、投资理财内部转账）放在更高 priority
（200+），显式设置两个账户即可覆盖 Layer 1/2。

### 8.6 跨字段 OR 合并：`fields` 数组语法（推荐）

当一个逻辑分类需要同时检查多个字段时（典型：peer **或** item
都包含同一关键词），`fields` 可以一条 condition 扫多个字段，
任一命中即满足。支持所有操作符。

**场景**：微信账单的"餐饮"既可能出现在 `peer`（交易对手）也可能出现在
`item`（商品描述），你希望一条规则覆盖。

```yaml
- name: "消费-餐饮美食"
  conditions:
    - field: type
      contains: 支出
    - fields: [peer, item]       # 任一字段命中即满足
      regex: 小吃|零食|火锅|串串|餐饮|中餐
  action:
    debit_account: Expenses:Food
  priority: 17
```

教育类同理，两行条件变一行：

```yaml
- name: "消费-教育文化"
  conditions:
    - field: type
      contains: 支出
    - fields: [peer, item]       # 任一命中即满足
      contains: 考
  action:
    debit_account: Expenses:Education
  priority: 18
```

`fields` 接受字符串数组，`field` 接受单个字符串，两者可同时存在
（合并为全量字段列表）。注意字段名必须是 `RawRecord` 标准字段或
`extra_fields` 中已映射的键。

正则操作符与 `fields` 配合时，捕获组取自**第一个命中的字段**的值。

### 8.7 替代方案：`match_mode: or`（仍支持）

在 `fields` 语法引入之前，跨字段 OR 用 `match_mode: or` 实现。
**除非 `fields` 无法覆盖（见下），否则优先用 `fields`。**

```yaml
# 可行但不再推荐（字段同模式时 fields 更简洁）
- name: "消费-餐饮美食"
  match_mode: or
  conditions:
    - field: peer
      regex: 小吃|零食|火锅|串串|餐饮|中餐
    - field: item
      regex: 小吃|零食|火锅|串串|餐饮|中餐
  action:
    debit_account: Expenses:Food
  priority: 17
```

这种方式需去掉 `type=支出` 约束（否则纯 OR 会误命中所有支出），
依赖更高 priority 的收入/投资规则覆盖。`fields` 无需此取舍。

**已知限制：`fields` 和 `match_mode: or` 都解决不了 `(A AND B) OR (A AND C)`。**

B 和 C 是不同字段、不同模式（如 peer 匹配 `滴滴|快车`，item 匹配
`骑行|站`）时，只能拆为两条规则，写同一个 `debit_account`。
分层规则体系下，最终结果完全一致。

## 9. 全量字段说明：`output`

可配置项：

- `date_format`（默认 `%Y-%m-%d`）
- `decimal_places`（默认 `2`）
- `account_prefix`
- `emit_open_directives`（默认 `false`）
- `open_date`（`YYYY-MM-DD`）
- `booking_method`（支持 `STRICT/FIFO/LIFO/AVERAGE/NONE`）

哪些场景需要配：
- 你要标准化输出小数位：配 `decimal_places`
- 你要输出 `open`：配 `emit_open_directives: true`
- 跨账期证券 lot 管理：建议 `booking_method: "FIFO"`

哪些场景可不配：
- 纯导入现金流水，不关心 open/commodity 时，可以全不配

## 11. 常见误区（避免踩坑）

### 11.1 继续使用旧字段名

以下旧字段已经移除，不再兼容：
- `default_asset_account/default_expense_account/default_income_account/default_currency`
- `default_cash_account/default_fee_account/default_pnl_account/default_rounding_account/default_repo_interest_account`
- `csv_options`
- `has_csv_header`

现在统一用：
- `default.*`
- `securities_accounts.*`
- `tabular_options`
- `has_header_row`

### 11.2 仍使用旧 mapping 路径

旧路径不再自动兼容：
- `mapping/<provider>.yml`
- `src/mapping/...`

请改为：
- `mapping/<category>/<provider>.yml`

### 11.3 只改了 provider，不改 global.providers

如果你在 `global.yml` 内也维护了 `providers.<name>`，请保证和独立 provider 文件一致，避免“同名双配置”产生行为差异。

### 11.4 `skip_header_lines` 与 `has_header_row` 组合错

高频错误：
- 把表头也跳过去了，导致映射列名全部失配。

建议排查顺序：
1. 确认原始文件第几行是表头
2. 设置 `skip_header_lines` 只跳说明区
3. 表头存在就 `has_header_row: true`

### 11.5 规则写了但没生效

优先检查：
- `field` 名是否真实存在（标准字段或 `extra`）
- `match_mode` 是否符合预期
- 是否被后续更高优先级（后执行）规则覆盖
- 是否被 `terminal: true` 提前截断

---

## 12. 推荐落地流程（团队可复制）

1. 先复制一个同类 provider 配置和 mapping 模板。
2. 只改四件事：
   - `mapping_file`
   - `default.*`
   - `skip_header_lines` / `has_header_row`
   - mapping 的列名
3. 用 10 条样本数据跑通。
4. 再加规则（从 2-3 条开始）。
5. 最后再调输出（`output`）。

## 14. 配置发布前的最终 Checklist

发布前逐项确认：

1. provider 名称与文件名一致。
2. `mapping_file` 指向分层路径。
3. 只使用新字段名（`default` / `securities_accounts` / `tabular_options` / `has_header_row`）。
4. `skip_header_lines` 与 `has_header_row` 已用真实样本核对。
5. mapping 至少覆盖场景最小必需字段。
6. 规则里使用的 `field` 在 `RawRecord` 标准字段或 `extra_fields` 中可取到。
7. 证券场景已确认 `symbol/quantity` 不会缺失。
8. 需要跨账期 lot 时已配置 `inventory_seed_files` + `output.booking_method`。
9. 全局 `providers` 与独立 provider 文件没有冲突（或只保留一种维护方式）。
10. 跑一遍：

```bash
cargo test --quiet
cargo run -- --provider <provider> --source <source> --config <provider.yml> --output <out.bean> --log-level info
```

## 15. 结论

如果你只想“快速可用”：
- 配好 `default + mapping + skip_header_lines/has_header_row` 就够了。

如果你想“长期可维护”：
- 再加规则分层（global + provider）和证券专用账户。

如果你想“跨账期稳定”：
- 再加 `inventory_seed_files + booking_method`。

## 18. 规则里 `field` 能写什么（超详细）

### 18.1 内置稳定字段

优先建议使用这些字段名：

- 文本：`payee`、`narration`、`transaction_type`、`type`、`status`、`reference`
- 证券文本：`symbol`、`security_name`
- 币种/对手：`currency`、`peer`、`peerAccount`
- 数值：`amount`、`quantity`、`unit_price`、`fee`、`tax`
- 日期：`date`

### 18.2 特殊语义

- `type`：先读 `extra.type`，若不存在再回退 `transaction_type`。
- 数值比较（`greater_than/less_than/between`）：
  - 对 `amount/quantity/unit_price/fee/tax` 优先用强类型值；
  - 其他字段会尝试从文本里清洗数字再解析。

### 18.3 你自定义的 `extra_fields` 也可直接匹配

例如你在 mapping 里配置了：

```yaml
extra_fields:
  merchantId: "商户单号"
```

规则就可以直接写：

```yaml
conditions:
  - field: "merchantId"
    not_empty:
```

## 19. “可不配”判断树（逆向决策）

如果你满足以下条件，可以不配对应项：

1. 不做跨账期证券 lot：
- 可不配 `inventory_seed_files`
- 可不配 `output.booking_method`

2. 不需要输出 `open` 指令：
- 可不配 `output.emit_open_directives`
- 可不配 `output.open_date`

3. 文件就是标准 UTF-8 CSV 且表头规范：
- 可不配 `tabular_options`（全部走默认）
- 可不配 `skip_header_lines`（默认 0）

4. 不做自动分类：
- 可不配 `rules`

5. 不在 global 里集中维护 provider：
- 可不配 `global.providers`

## 20. 日志到配置的故障定位表

| 现象/日志 | 大概率原因 | 优先检查项 |
|---|---|---|
| `Mapping field 'xxx' references column ... not in source headers` | 列名不匹配，或表头行没读对 | `skip_header_lines`、`has_header_row`、mapping 列名 |
| `Missing date` | `date` 未映射且兜底列也没命中 | mapping `date`、`date_formats`、源日期列名 |
| `Missing amount`（现金流） | `amount` 未映射，且收入/支出分列推断失败 | mapping `amount` 或源列是否在推断键集合 |
| `Missing security symbol` | 证券 mapping 未映射 `symbol` | mapping `symbol` |
| `Missing quantity` | 证券 mapping 未映射 `quantity` | mapping `quantity` |
| `Missing cash amount and unit price` | 证券 `amount` 和 `unit_price` 都缺失 | mapping 至少补一个 |
| `No field mapping file found` | `mapping_file` 路径错或文件缺失 | `mapping_file`、分层目录路径 |
| `Field count mismatch` | CSV 列数不齐且策略不允许跳过 | `tabular_options.flexible`、`--strict`、源文件质量 |

## 21. `strict` 与 `tabular_options.flexible` 组合语义

> 这块最容易误解，单独列出来。

| `--strict` | `flexible` | CSV 解析坏行 | 字段映射错误 |
|---|---|---|---|
| `false` | `false` | 失败退出 | 记录 warning，继续 |
| `false` | `true` | warning，继续 | warning，继续 |
| `true` | `false` | 失败退出 | 失败退出 |
| `true` | `true` | 失败退出 | 失败退出 |

建议：
- 日常批量导入：`strict=false + flexible=true`
- 回归测试/发布验收：`strict=true`
